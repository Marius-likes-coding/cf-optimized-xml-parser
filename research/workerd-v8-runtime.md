### Non-default V8 flags workerd sets

In `V8System::init()`, `src/workerd/jsg/setup.c++` [source]:

* `--noincremental-marking` — always. Comment: JSG GC integration not trusted with incremental marking; Worker heaps small (128MB noted); revisit only after stress testing.
* `--js-source-phase-imports` — always.
* `--single-threaded-gc` — `#ifdef __APPLE__` only (macOS arm64 workaround for "collecting pages containing compiled code").
* `--expose-gc` — only if `isPredictableModeForTest() || isGcStressModeForTest() || isAllocGcStressModeForTest()`.

No `--jitless/--noopt/--single-threaded`, no Maglev/Turbofan kill-switches in `setup.c++`, `.bazelrc`, `v8.MODULE.bazel` [inference from absence]. Isolate-level hardening in same file [source]: `SetMicrotasksPolicy(kExplicit)`, `SetAllowAtomicsWait(false)` ("might allow DoS"), `SetModifyCodeGenerationFromStringsCallback` eval gate (empty `new Function()` allowed, else `EvalError`), `SetAllowWasmCodeGenerationCallback` tied to `evalAllowed`, CppGC `kAtomic/kAtomic` (explicitly rejects incremental/concurrent marking/sweeping: "CPU cores fully utilized; small heaps").

### Build: pointer compression, sandbox, cages

* workerd sets no `v8_enable_pointer_compression / v8_enable_sandbox / cage` GN args in-repo [inference]: `build/deps/v8.MODULE.bazel` only pins `VERSION/INTEGRITY/PATCHES` [source]; `.bazelrc` V8 bits are only `v8_use_perfetto`, `-O3` for `v8/src`/abseil/boringssl/simdutf/ICU/perfetto/zlib/tcmalloc, `-fno-exceptions`, sanitizer defines, macOS `heap.cc -O3` workaround [source](https://raw.githubusercontent.com/cloudflare/workerd/main/.bazelrc); `build/workerd-v8/` is only an ICU-data shim [source].
* Upstream defaults (V8 12+, still true 15.x): `v8_enable_pointer_compression` defaults true on x64/arm64; Maglev requires `turbofan && (x64|arm64) && pointer_compression`; sandbox "enabled by default on supported 64-bit configs" [3rd-party](https://chromium.googlesource.com/v8/v8/+/main/BUILD.gn) / [3rd-party](https://chromium.googlesource.com/v8/v8.git/+/refs/heads/main/src/sandbox/README.md). Outdated advice to disable pointer compression for speed predates V8 12 and is wrong for 15.x [inference].
* workerd code assumes cages exist: `setup.c++` `#ifdef V8_COMPRESS_POINTERS_IN_MULTIPLE_CAGES` → `NewDefaultAllocator(group)` else `NewDefaultAllocator()`; `newIsolateGroup()` → `IsolateGroup::Create()` if `CanCreateNewGroups()`; `setup.h` `Isolate` template takes `v8::IsolateGroup` with "4GB V8 heap per group" comment [source]. `docs/jsg.md` says "When V8 sandboxing is enabled... default group... what workerd uses in production" — conditional wording, not proof [docs].
* Counter-evidence: `patches/v8/0039-Fix-TSan-build-without-the-V8-sandbox.patch` says "Workerd builds V8 without the sandbox" and guards `kIndirectPointer` with `#if V8_ENABLE_SANDBOX` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/patches/v8/0039-Fix-TSan-build-without-the-V8-sandbox.patch). Report as: sandbox **off** in OSS build per patch comment; pointer compression assumed **on** (x64/arm64 default + cage code). No in-repo GN flag to cite; verify at runtime via `PointerCompressionIsEnabled()/SandboxIsEnabled()` — no evidence in OSS [inference]. Patch list (41 on main, 38 at 15.1) is toolchain + JSG APIs, not JIT-tier switches [source].

### JIT tiers

* No workerd config disables JIT [inference]. Expected V8 15.1: Ignition + Sparkplug (baseline) + Maglev (mid-tier) + Turboshaft/Turbofan (top-tier); Turbolev (`--turbolev`, Maglev→Turboshaft frontend) emerging upstream [3rd-party].
* workerd acknowledges all three optimizing tiers: `setup.h` `codeMap` warning lists `--concurrent_recompilation, --concurrent_sparkplug, --maglev_build_code_on_background, ...` — "Callers who configure V8 with any of the following MUST account for this" [source]. `setup.c++` `jitCodeEvent()` handles `CODE_ADDED/MOVED/REMOVED` for stack traces; comment notes V8 14.9+ can deliver events from background threads [source].

### Production vs OSS

Same core, extra defense outside OSS [docs](https://github.com/cloudflare/workerd/blob/main/README.md): "`workerd` is not a hardened sandbox... must run inside VM. Cloudflare Workers hosting uses many additional layers." Internal differences [source]: `v8.MODULE.bazel` "indirect through `@workerd-v8` to allow dependents to override... overridden in internal non-OSS repo"; `setup.h` "Our internal embedder disables all of the above [concurrent JIT flags], so `jitCodeEvent` only fires on main thread" (OSS `codeMap` is lock-free and races if concurrent JIT enabled); `autogates` (`workerd.capnp @4`), internal `ew/workerd` merge refs, nightly V8 CI. Legacy `Isolate` ctor comment "Currently used by non-sandboxing edgeworker, but deprecated" suggests prod history includes non-sandbox mode — do not over-claim current prod sandbox state [inference].

## 2. Memory

* Canonical limit: `Memory per isolate 128 MB`, Free == Paid, per-isolate not per-invocation, single isolate handles many concurrent requests [docs](https://developers.cloudflare.com/workers/platform/limits/). 128MB = `128*1024*1024 = 134,217,728` bytes [inference].
* What counts: only `JS heap + WebAssembly` named [docs]. ArrayBuffers, external strings, C++ memory, SQLite: **no evidence in docs or OSS** [inference]. Metrics page says chart shows "V8 isolate memory... shares memory across concurrent requests" [docs](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/).
* On exceed: lets in-flight complete, creates new isolate for subsequent; under extreme load may cancel incoming [docs]. Error: `Error 1102 Worker exceeded resource limits`, dashboard `Exceeded Memory`, analytics/Logpush `exceededMemory`, plus `Memory limit would be exceeded before EOF` when buffering response body [docs](https://developers.cloudflare.com/workers/platform/limits/) / [docs](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1102). Schema: `src/workerd/io/outcome.capnp:27 exceededMemory @8` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/io/outcome.capnp), `trace-stream.c++:47 V(EXCEEDEDMEMORY)`, `io-context.h:57 throwExceededMemoryLimit()`, `io-context.h:1679-1685` `hasExcessivelyExceededHeapLimit()` → `OVERLOADED "Worker has exceeded memory limit"` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/io/io-context.h).
* OSS does **not** enforce 128MB: `src/workerd/server/server.c++:3329-3399` `NullIsolateLimitEnforcer::getCreateParams(){return {};}`, `exitJs()->false`, `hasExcessivelyExceededHeapLimit()->false` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/server/server.c++). Interface is `src/workerd/io/limit-enforcer.h` (`getCreateParams/customizeIsolate/exitJs/hasExcessivelyExceededHeapLimit/getBlobSizeLimit/getTrackedWasmInstances`) [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/io/limit-enforcer.h). Real enforcer is closed-source, "very platform-specific, relying on non-portable Linux kernel features" per kentonv/jasnell in [source](https://github.com/cloudflare/workerd/issues/49). No `ISOLATE_LIMIT`, no `134217728` heap constant, no `ResourceConstraints`/`SetHeapLimit`/`GetHeapStatistics`/`Reached heap limit`/semi-space tuning in OSS `jsg,io,server` [source — verified by grep]. `128*1024*1024` literals that exist are other limits: `limit-enforcer.h:109 getBlobSizeLimit()=128MB` (buffering), `server.c++:3340 ActorCache 16/128MB`, `worker.c++:3362 inspector WS 128MB [source].
* V8 mechanism (general, not workerd-specific): `v8::ResourceConstraints::ConfigureDefaultsFromHeapSize`, `set_max_old/young_generation_size_in_bytes`, `CreateParams::constraints/heap_limits`, `AddNearHeapLimitCallback` [3rd-party](https://v8.github.io/api/head/classv8_1_1ResourceConstraints.html). Production `getCreateParams()` likely sets 128MiB + NearHeapLimit handler that condemns isolate rather than crash [inference — no source].
* Heap config details: `V8System::init` sets process-wide `SetFatalMemoryErrorCallback(oomError)` + per-isolate `SetOOMErrorHandler`; `oomError()` distinguishes `"JavaScript heap out of memory"` vs `"process out of memory"` (`setup.c++:110-160,454,560`) [source]; `newIsolate()` sets `NewDefaultAllocator()` + CppGC, no `CreateParams.constraints` in OSS [source]; only `128MB` mention in `jsg/` is the `--noincremental-marking` comment [source].
* External memory: `jsg/jsg.c++:468-588 ExternalMemoryTarget` + `AdjustAmountOfExternalAllocatedMemoryImpl` (exposed by `patches/v8/0030`) pressures GC; used for subrequests (`io-context.c++:1117,1237 js.getExternalMemoryAdjustment(8*1024)`) [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/jsg/jsg.c++). Pressures GC, does not enforce limit [inference]. `memoryCacheProvider` is Cache API, unrelated to heap [source]. `GetHeapSize()/GetExternalMemory()` fast-path patch `0020` exists because `GetHeapStatistics()` "performs non-trivial computation", but has no caller in OSS [source].
* GC between requests: **no evidence in docs or OSS** [inference]. Only `gcPrologue/Epilogue` hooks are `LockTiming` metrics in `observer.h` [source]. Open issue `workerd#6824` notes standalone workerd climbs to cgroup cap with minor-GC-only under load; forced GC reclaims 600MB→77MB [source](https://github.com/cloudflare/workerd/issues/6824).
* Concurrency: no fixed number. "Single instance runs hundreds/thousands isolates", "single isolate may handle multiple including concurrent in single-threaded event loop... during await" [docs](https://developers.cloudflare.com/workers/reference/how-workers-works/). Code: `src/workerd/io/worker.h:94-99` "each script loaded into single Worker reused by multiple requests, one thread at a time"; `takeAsyncLock()` fair queue + `Worker::Lock`; per-request `IoContext_IncomingRequest`, actors share one `IoContext` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/io/worker.h). No per-request heap partition [inference].

## 3. CPU time

* Definition: "CPU time measures how long CPU spends executing Worker code. Waiting on fetch/KV/DB does **not** count" [docs](https://developers.cloudflare.com/workers/platform/limits/).
* Implementation lives behind closed enforcer: OSS `src/workerd/io/` has `limit-enforcer.h` but **no** `limit-enforcer.c++`; no `getCpuTime()` in `io/observer.h` or `jsg/observer.h`; `io-timers.h` is only timer queue (`MAX_TIMEOUTS=10'000`) [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/io/limit-enforcer.h). Accounting model [inference]: production `enterJs()` starts per-request meter, isolate-unlock on I/O stops it — why "waiting doesn't count" without V8 instrumentation. Exact clock (`CLOCK_THREAD_CPUTIME_ID` vs cgroup vs V8 `GetCpuTime`) not published [inference].
* What counts [docs + inference]: JS execution (loops, `JSON.parse`, regex, `TextDecoder`, `Response.text()`, sync WebCrypto, Wasm exec/compile on main thread) — yes; major/minor GC pause on main thread — must count (same-thread; Kenton Varda 2018: 3MB `JSON.parse` → ~30MB heap "will trigger GC pauses" hitting CPU limit [3rd-party](https://community.cloudflare.com/t/how-do-we-know-the-cpu-timing/13799)); native C++ while holding isolate lock — yes (indistinguishable to thread meter); background concurrent GC/JIT threads — unknown, likely no/partial [inference, do not assert without qualification]; `await fetch/KV/R2/D1`, timer wait, idle — no [docs]; startup global scope — separate 1s budget via `enterStartupJs` [source], error `10021 Script startup exceeded CPU time limit` [docs].
* Reported as: `src/workerd/io/trace.h Trace { cpuTime, wallTime }`, `worker-interface.capnp Trace { cpuTime @10, wallTime @11, Outcome { cpuTime @1, wallTime @2 } }`, `outcome.capnp exceededCpu @3` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/io/worker-interface.capnp) → `EventDispatcher::sendTraces()` → Tail Worker. Surfaced since 2025-04-09 changelog in invocation log + Tail top-level + Logpush top-level [docs](https://developers.cloudflare.com/changelog/post/2025-04-09-workers-timing/); Logpush dataset `CPUTimeMs` / `WallTimeMs` ("wall = JS context open, incl. `waitUntil()`") [docs](https://developers.cloudflare.com/logs/logpush/logpush-job/datasets/account/workers_trace_events/). capnp `UInt64` ns → ms divisor undocumented [inference].
* Timers/Spectre: `performance.now()` + `Date.now()` only advance after I/O — `e-s==0` for pure-compute loop in production; local `wrangler dev` increments normally [docs](https://developers.cloudflare.com/workers/runtime-apis/performance/). `Date.now()` locked to last I/O, no timers/threads/shared memory since 2017; dynamic process isolation + rescheduling (TU Graz [3rd-party](https://arxiv.org/pdf/2110.04751)) [docs](https://developers.cloudflare.com/workers/reference/security-model/). Published rounding (1ms/5µs browser-style): none — behavior is freeze, not clamp [docs]. Do not cite browser coarsening for Workers. Sub-ms oracle via external WebSocket timestamps is [3rd-party](https://browserinsight.net/blog/browser-timer-precision).
* Limits (Sep 2026) [docs](https://developers.cloudflare.com/workers/platform/limits/) / [docs](https://developers.cloudflare.com/workers/platform/pricing/) / [docs](https://developers.cloudflare.com/changelog/post/2025-03-25-higher-cpu-limits/): HTTP Free 10ms / Paid max 5min default 30s (`limits.cpu_ms=300_000` in wrangler.jsonc/toml or dashboard); Cron Free 10ms / Paid 30s (<1h interval) or 15min (≥1h); Queue/DO-alarm 15min CPU (wall 15min); Workflows per-step default 30s/up to 5min, unlimited wall; startup 1s both plans; wall HTTP unlimited while client connected (`waitUntil()` +30s); avg Worker ~2.2ms, parse/SSR 10–20ms; overrun → `1102`, `exceededCpu`; billing Paid $5/mo incl. 10M req + 30M CPU-ms, +$0.30/M req, +$0.02/M CPU-ms. Worker size now 64MiB uncompressed both plans (older 3/10MB tables are pre-Sep-2026) [docs].

## 4. Native APIs that matter for a parser

* `TextDecoder` uses **both** ICU (general) and simdutf (narrow fast paths) + Rust `encoding_rs` for legacy — not simdutf-everywhere [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/encoding.c++). `IcuDecoder::create` → `ucnv_open()`, fatal → `UCNV_TO_U_CALLBACK_STOP`; `decode()` → `ucnv_toUnicode()` into `KJ_STACK_ARRAY(UChar,...,512,4096)` → `js.str()` (UChar=UTF-16 → `NewFromTwoByte`, two-byte string) [source]. Covers utf-8, utf-16le/be, iso-8859-*, windows-1250/51/53-58, gb18030-when-CJK-flag-off, etc. [source].
* `LegacyDecoder` (`encoding-legacy.h/.c++`, `src/rust/encoding/lib.rs` wrapping `encoding_rs` via CXX) outputs `&[u16]` UTF-16 → `js.str()` → always `NewFromTwoByte` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/encoding-legacy.h). Routing [source]: always legacy: `Windows_1252`, `X_User_Defined`; conditionally legacy: `Big5,Euc_Jp,Euc_Kr,Gb18030,Gbk,Iso2022_Jp,Shift_Jis` iff `FeatureFlags textDecoderCjkDecoder` else ICU; rest → ICU.
* simdutf inside `IcuDecoder::decode` only when no pending bytes [source]: utf-8 + `simdutf::validate_ascii()` → `return js.str(buffer)` ("interpret as Latin1... v8 allocates these more efficiently"); utf-16le even-length no-split-lead-surrogate → aligned copy → `js.str()`; optional `validate_utf16/to_well_formed_utf16` behind `textDecoderReplaceSurrogates`. No simdutf transcoders in decode path otherwise [source+inference]. Contrast: `TextEncoder::encode/encodeInto` (behind `AutogateKey::ENABLE_FAST_TEXTENCODER`) uses `utf8_length_from_latin1/convert_latin1_to_utf8/convert_utf16_to_utf8/...` [source]; `node/buffer.c++` uses simdutf only for base64 + `isAscii/isUtf8` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/node/buffer.c++).
* One-byte vs two-byte outcome (`src/workerd/jsg/jsvalue.h` `Lock::str` overloads, V8≥15 branches; `jsg/util.h v8Str`) [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/jsg/jsvalue.h): `str(ArrayPtr<byte>)` → `NewFromOneByte` (one-byte/latin1); `str(ArrayPtr<char>)` → `NewFromUtf8`; `str(ArrayPtr<char16_t>)` → `NewFromTwoByte` (two-byte). Consequences [source+inference]: `TextDecoder('utf-8').decode(asciiBytes)` → `validate_ascii` hit → **one-byte, no ICU, no copy beyond V8 alloc**; non-ASCII utf-8 → ICU → two-byte; `TextDecoder('ascii'/'latin1'/'windows-1252'/'iso-8859-1'/...)` → all map to `Windows_1252` (`EW_ENCODING_LABELS`) → `LegacyDecoder` → **always two-byte even for pure ASCII**; utf-16le fast path → two-byte; no `MakeExternal` in any decoder path. Commit "fix windows-1252/latin1/ascii #6030" could not be verified by number; current `main` behavior above is verified [inference].
* `Response.text()/arrayBuffer()` chain [source]: `api/http.c++ Body::text/arrayBuffer/blob/bytes/json` → `api/js-readable-stream.c++ JsReadableStream::text/arrayBuffer` → `ReadableStreamController::readAllText/readAllBytes` → `api/streams/standard.c++ ReadableStreamJsController::readAll<T>/AllReader::loop/allText/allBytes`. `text()`: null → empty without `IoContext`; else disturbed-check, `getBufferingLimit()`, returns `Promise<kj::String>` wrapped via `NewFromUtf8` (UTF-8 validated by V8) [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/http.c++). `arrayBuffer()` → `JsRef<JsArrayBuffer>`; `blob()=arrayBuffer()+Content-Type`; `bytes()` wraps buffer; `json()=text()+parseJson` [source]. `AllReader::loop` requires ArrayBuffer/View chunks, enforces limit with `"Memory limit exceeded before EOF."` (prompt's "would be exceeded" wording not found), **defensively copies every chunk** (`parts.add(copy())`, comment: detach/resize hazard + "double copy required"), `allBytes`: `create(runningTotal)+copyInto` (2nd copy); `allText`: `heapArray(runningTotal+1)+copyInto` + BOM-strip/NULL-terminate, length-checked vs `kMaxLength` [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/api/streams/standard.c++). So `text()` = chunk-copy + concat-copy + `NewFromUtf8` decode (3 touches); `arrayBuffer()` = chunk-copy + concat-copy (2 copies) [source+inference]. Buffer-backed/tee bodies avoid re-pull, not concat copies.
* JSG call overhead: every `decode/text/arrayBuffer` is `JSG_METHOD` on `JSG_RESOURCE_TYPE` (`api/encoding.h`, `api/http.h`) → `jsg.h registerMethod` → V8 `FunctionTemplate` slow callback (`jsg/resource.h`): `FunctionCallbackInfo` parsing, `TypeWrapper` conversion, `HandleScope`, lock assert, exception translation [source](https://raw.githubusercontent.com/cloudflare/workerd/main/src/workerd/jsg/jsg.h). V8 Fast API exists (`jsg/fast-api.h`, `isFastApiCompatible`) but **does not apply** — signatures take `Lock&`, `Optional<Array<byte>>`, `JsString`, return `JsString/Promise` (none fast-compatible) [source+inference]. Each `decode(chunk)` also pays ICU/Rust state + `reset()` on flush; `Response.*` pays promise + `evalNow` + limit-enforcer fetch [inference].

## Actionable rules for the parser

* Accept `string` input as primary path; accept bytes only via single `TextDecoder('utf-8').decode(bytes)` once — never `Response.text()` per request (3 touches + promise) and never per-chunk `decode({stream:true})` in a loop (JSG + ICU/Rust state per call).
* Never request `ascii/latin1/windows-1252` decoders to "save" — in workerd they all go `LegacyDecoder` → always two-byte strings; `utf-8` on ASCII gives the only one-byte fast path (`validate_ascii` → `NewFromOneByte`).
* Keep everything one-byte as long as possible: ASCII XML parsed from a one-byte input stays cheap; first non-ASCII char forces ICU two-byte output — branch ASCII/non-ASCII early if you specialize.
* Zero-copy slices keeping input alive is correct: limit is per-isolate (shared across concurrent requests), not per-request; retaining input for request lifetime is free, retaining across requests leaks 128MB shared heap.
* Minimize live set: `{name,attrs,children}` + sliced strings only; drop whitespace-only nodes (already decided); avoid intermediate arrays/copies — `AllReader` already double-copies bodies, do not add a third.
* Assume `--noincremental-marking` (stop-the-world only): long synchronous parses pause the isolate; prefer tight loops with few allocations over elegant allocations; large temporaries directly inflate main-thread GC which counts toward CPU time.
* Minimize JSG crossings: no per-token native calls; do all parsing in pure JS in one go; batch any I/O.
* No `eval/new Function` (blocked), no Node `Buffer` (Web APIs only); Wasm only as precompiled module — pure-JS tuning beats Wasm-compile CPU cost for typical XML sizes.
* Do not self-time with `performance.now()/Date.now()` in production (frozen without I/O) — measure from Tail Workers `cpuTime/wallTime` or Logpush `CPUTimeMs`, profile locally with DevTools.
* Size for Free 10ms: typical parse budget is 10–20ms for heavy payloads; Paid default 30s/max 5min — design chunking/fail-fast for >10ms inputs if Free must pass.

## Open questions that need a benchmark

* Actual prod V8 flags (pointer compression/sandbox/cages, concurrent-JIT disabled?) — closed-source; probe via `--allow-natives-syntax` intrinsics locally vs prod behavior difference.
* One-byte vs two-byte parse throughput on V8 15.1 for this parser's access pattern (charCodeAt/charAt/slice/indexOf) and at what non-ASCII fraction the `utf-8` ICU path loses to manual handling.
* `string` input vs `Uint8Array + single utf-8 decode` vs `Response.arrayBuffer()+decode` vs `Response.text()`: copy-count and `NewFromUtf8` validation cost for 10KB/1MB/10MB XML.
* Per-call JSG cost: single `decode()` vs chunked `decode(stream:true)` (N=1/10/100 chunks) for same bytes.
* Peak heap + GC pauses under `--noincremental-marking` for deep vs wide trees; `slice()` (SlicedString, keeps parent) vs `substring()` (copy) memory/speed tradeoff at parser's slice sizes.
* Whether `globalThis.gc()` + `--expose-gc` via `MINIFLARE_WORKERD_V8_FLAGS` is wired locally for deterministic memory benches; `wrangler` upgrade needed from `^4.26.0`.
* External-memory accounting: does holding large `Uint8Array` + decoded string double-count toward 128MB eviction in prod (weaknesses in OSS visibility).
* Local `.cpuprofile`/heap snapshot vs prod `cpuTime` ratio: calibration factor for this workload (local CPU ≠ Cloudflare CPU).
