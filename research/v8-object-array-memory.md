# V8 object/array memory layout for a tree-building XML parser

Target: V8 15.1 / workerd 1.20260815, 64-bit, pointer compression ON (the workerd default; see scope note). All claims are for V8 12–15 (2023–2026) unless flagged otherwise.

Scope note: Cloudflare Workers isolates are 128 MB (JS heap + Wasm, per isolate, not per request) and CPU-time limited (10 ms free / up to 5 min paid) — [docs] https://developers.cloudflare.com/workers/platform/limits. workerd embeds V8 with isolates, no threads/shared memory, single-threaded event processing — [docs] https://developers.cloudflare.com/workers/reference/security-model. workerd is built from https://github.com/cloudflare/workerd. I found no evidence workerd disables pointer compression or the V8 sandbox; assume compressed tagged values (4 bytes) throughout, so use the "compressed" column below.

Legend: [source] = verified in V8/workerd source, [docs] = maintainer docs/blog, [3rd-party] = others' benchmark/post, [inference] = my reasoning. "No evidence found" is stated explicitly where applicable.

Related design note from `ideas.md`: the parser is depth-first single-pass with a stack of open elements (fail on misnesting / trailing content after the stack drains). That design is assumed below; breadth-first or two-ends recursion is strictly worse [inference].

## 1. Exact byte sizes (pointer compression on vs off)

Authoritative layout doc: `docs/heap/objects-and-maps.md` — JSObject = Map + Properties + Elements + in-object fields — [docs] https://chromium.googlesource.com/v8/v8/+/HEAD/docs/heap/objects-and-maps.md. Pointer compression = 32-bit offsets in a 4 GB cage (heap limit ≤ 4 GB when on) — [docs] https://v8.dev/blog/pointer-compression.

| Piece | Compressed (workerd; `kTaggedSize=4`) | Uncompressed 64-bit (`kTaggedSize=8`) | Constant / source |
|---|---|---|---|
| One tagged slot | 4 B | 8 B | `kTaggedSize` in `src/common/globals.h` [source] via https://github.com/v8/v8/blob/main/src/objects/js-objects.h (see `kTaggedSize`, `TAGGED_SIZE_8_BYTES`) |
| `HeapObject` header (just `map_`) | 4 B | 8 B | `class HeapObject { TaggedMember<Map> map_; }`, `src/objects/heap-object.h` [source] |
| `JSReceiver` header (map + properties) | 8 B | 16 B | `properties_or_hash_` in `src/objects/js-objects.h` [source] |
| `JSObject::kHeaderSize` (map + properties + elements) | **12 B** (offsets 0,4,8) | **24 B** (offsets 0,8,16) | `JSObject::kHeaderSize = sizeof(JSObject)`, `Internals::kJSObjectHeaderSize = 3*kApiTaggedSize` in `src/objects/js-objects.h` + `include/v8-internal.h` [source] |
| `JSArray::kHeaderSize` (JSObject + `length_`) | **16 B** (`kLengthOffset=12`) | **32 B** (`kLengthOffset=24`) | `JS_ARRAY_FIELDS: V(kLengthOffset,kTaggedSize)`, `src/objects/js-array.h` [source] https://github.com/v8/v8/blob/main/src/objects/js-array.h |
| `FixedArray::kHeaderSize` (map + `length_` u32) | **8 B** | **16 B** (4 map + 4 length + 4 pad) | `FixedArrayBase::kHeaderSize`, `kLengthOffset`, `kPaddingOffset` in `src/objects/fixed-array-base.h`, `src/objects/fixed-array.h` [source] |
| `FixedArray` payload | 4 B/element | 8 B/element | `SizeFor(cap) = header + cap*kTaggedSize`, `kMaxFixedArrayCapacity = 128M` (1M in lower-limits mode), `src/objects/fixed-array.h` [source] |
| `PropertyArray` header (`map` + `length_and_hash_`) + payload | 8 B + 4 B/field | 16 B + 8 B/field | `SizeFor(len)`, `kMaxLength = 1023` (`LengthField 10 bits`), `src/objects/property-array.h` [source] |
| In-object property slot | 4 B | 8 B | same `kTaggedSize` [source] |

| `JSObject::kMaxInObjectProperties` | 252 | 252 | `(kMaxInstanceSize − kHeaderSize) >> kTaggedSizeLog2`, `kMaxInstanceSize = 255*kTaggedSize`, `src/objects/js-objects.h` [source] |
| Shared empties | **0 B marginal**: zero-length `FixedArray`/`PropertyArray`/elements/properties all point at the `empty_fixed_array` root | same | `RootsTable V(FixedArray, empty_fixed_array, EmptyFixedArray)`, `src/roots/roots.h`; `FixedArray::New(0) → empty_fixed_array()`, `RightTrimOrEmpty/ShrinkOrEmpty(0) → empty_fixed_array()`, `src/objects/fixed-array-inl.h`, `src/objects/fixed-array.cc`; `NewJSArray` uses `kEmptyFixedArray` for properties+elements, `src/objects/js-array.tq` [source] |

Worked examples (compressed, incl. alignment to 8) [inference from the constants above]:

- `{name, attrs, children}` node, all in-object: 12 + 3×4 = **24 B** for the node itself (properties/elements pointers aim at `empty_fixed_array`, no extra). Children backing store is separate (see arrays).
- `{name, attrs}`: 12+8 = 20 → **24 B** with 4 B filler.
- `{}`: **12 B**. `{id:"1"}`: 12+4 = **16 B**.
- `[]`: `JSArray` **16 B**, elements = shared empty (0 B). `["id","1"]`: 16 + (8+2×4) = **32 B**. `[name,attrs,children]` tuple node: 16 + (8+12) = **36 → 40 B** aligned.
- So attrs-as-object `{id:"1"}` (16 B total) is ~half the memory of attrs-as-flat-array `["id","1"]` (32 B total) for the 1-attribute case; empty attrs `{}` (12 B) vs `[]` (16 B) vs `null` (**0 B**, an Oddball root, no allocation) [inference].

What changed / outdated advice to flag: pre-2020 (pre-pointer-compression, V8 ≤ 7.x) sizes were ~2× larger (8-byte slots); any blog quoting "JSObject header = 24 bytes / array = 32 bytes" without qualification is the uncompressed figure and **outdated for workerd** (compression shipped 2020, V8 8.x — [docs] https://v8.dev/blog/pointer-compression). 32-bit-binary examples (e.g. "instance size 52" in the 2020 slack-tracking post — [docs] https://v8.dev/blog/slack-tracking) use 4-byte words for a different reason; do not copy those absolute numbers, only the mechanism.

## 2. Hidden classes (Maps), in-object slots, transitions, dictionary mode

- Same shape ⇒ same Map. Objects with the same properties added in the same order share the Map; each added named property creates a new Map linked by a transition; order matters (`{a,b}` and `{b,a}` are different Maps) — [docs] https://v8.dev/blog/fast-properties, https://v8.dev/docs/hidden-classes, https://chromium.googlesource.com/v8/v8/+/HEAD/docs/runtime/hidden-classes-and-ics.md. Indexed (`a[0]=…`) stores do **not** create new Maps — [docs] https://v8.dev/blog/fast-properties.
- Object literals get an exact-size boilerplate map (no guessing): `Runtime_CreateObjectLiteral → CreateLiteral`, `src/runtime/runtime-literals.cc` [source]. `{}` gets the initial empty map; `{a,b,c}` walks 3 transitions at creation. No per-instance resizing if you never add more keys afterwards [inference].
- `class`/`constructor` instances get **slack tracking**: initial map over-allocates in-object space, reclaims after ~7 constructions. Constants: `Map::kSlackTrackingCounterStart = 7`, `kSlackTrackingCounterEnd = 1`, `kGenerousAllocationCount = 7`, `src/objects/map.h` [source]; mechanism + "mystical magic number seven" + `JSFunction::CalculateExpectedNofProperties` + worked 2-props-plus-8-slack example — [docs] https://v8.dev/blog/slack-tracking; summary — [docs] https://github.com/v8/v8/blob/main/docs/objects/fields-and-elements.md. Practical effect: the first ~7 `new Node()` instances are **bloated** (up to ~8+ spare slots in the blog's example); after that instances are trimmed to the observed max (`ComputeMinObjectSlack`). Object literals at a single site do not pay this warmup [inference — slack tracking is driven by the constructor's initial map; literals use precomputed boilerplates].
- Adding keys one at a time (`o={}; o.name=…; o.attrs=…; o.children=…`) follows the **same transition tree** and converges on the same final Map as the literal *if the order matches* — [docs] https://v8.dev/blog/fast-properties — but each store is a separate Map transition + IC update at parse time, i.e. slower to build than one literal [inference].
- What pushes an object into dictionary (slow) mode — [source] unless noted:
  - `delete o.k` normalizes to dictionary (`NormalizeProperties(..., CLEAR_INOBJECT_PROPERTIES, ...)`) — `src/objects/js-objects.cc`, `src/objects/map-inl.h` [source]. Never `delete` on hot nodes.
  - Too many descriptors: `kMaxNumberOfDescriptors = 1020` (`kDescriptorIndexBitCount = 10`), `src/objects/property-details.h` [source]. Past that, `NormalizeProperties`.
  - Too many keyed additions past in-object slack with no spare fields: `Map::TooManyFastProperties` vs `fast_properties_soft_limit = 12` (`src/flags/flag-definitions.h`, `src/objects/map-inl.h`) [source]. I.e. objects grown via `o[k]=v` with >~12 out-of-object fields risk slow mode.
  - `__proto__` as a data key / assigning `o.__proto__ = …` mutates the prototype instead of creating a field and forces slow paths; defining a literal `{"__proto__":…}` likewise does not create an own data property (spec behavior). Keep the literal keys fixed to `name/attrs/children` and never use `__proto__` as an attr name without mapping it [inference + spec; no V8 source link verified for the exact normalize trigger — needs a benchmark/check].
  - `Object.create(null)` itself does **not** mean dictionary mode: it uses a null-prototype fast map (`Map::GetObjectCreateMap`, `src/objects/map-inl.h`) [source]; it only goes dictionary on the same triggers above. It does cost a second transition tree (null-prototype maps are distinct from `Object.prototype` maps), so don't mix `{}`-prototype and null-prototype nodes at one site [inference].
- Property **representation** tracking (`kSmi/kDouble/kHeapObject/kTagged` in `src/objects/property-details.h` — [docs] https://chromium.googlesource.com/v8/v8/+/HEAD/docs/objects/fields-and-elements.md): a field that sometimes holds `null` and sometimes an object degrades that field's representation to general `Tagged` in the shared Map. That is a mild access cost, not a size cost, and is unavoidable if one field is polymorphic — but keep the *set of shapes* at one allocation site to exactly 1 (same keys, same order) so there is exactly 1 Map, not N [inference].

## 3. Arrays: elements kinds, growth, `slice()`, `new Array(n)`, shrinking

- Backing stores: `PACKED_SMI_ELEMENTS` (`FixedArray` of Smis) → `PACKED_DOUBLE_ELEMENTS` (`FixedDoubleArray`, unboxed doubles) → `PACKED_ELEMENTS` (`FixedArray` of tagged values), each with a `HOLEY_*` twin; full lattice has ~21 kinds (`src/objects/elements-kind.h`) — [docs] https://v8.dev/blog/elements-kinds, https://chromium.googlesource.com/v8/v8/+/HEAD/docs/objects/fields-and-elements.md.
- Transitions are **one-way and sticky**: specific → general, packed → holey, never back (except a 2025 `Array.prototype.fill` exception). Once holey, always holey even after filling — [docs] https://v8.dev/blog/elements-kinds. Holey costs extra hole/prototype checks on every op — [docs] https://v8.dev/blog/fast-properties, https://v8.dev/blog/elements-kinds.
- For this parser every children/attrs array holds objects/strings, so the only kinds that matter are `PACKED_ELEMENTS` (good) vs `HOLEY_ELEMENTS` (bad). `-0`/`NaN`/`Infinity` forcing `DOUBLE` is irrelevant here (no numeric elements) [inference].
- Growth formula on `push` past capacity — `JSObject::NewElementsCapacity`, `src/objects/js-objects.h` [source]:
  `new = old + (old >> 1) + 16` (`kMinAddedElementsCapacity = 16`), capped at `kMaxFixedArrayCapacity`. So growth is ~1.5× + 16 slots; each growth allocates a new `FixedArray` and copies. Empty-array first push additionally consults `JSArray::kPreallocatedArrayElements = 4` (`src/objects/js-array.h`) [source]. A per-node `children=[]` + N pushes therefore over-allocates (up to ~50% slack) and copies O(log) times; a 1-child node can sit on a ~16-slot backing if grown from 0 — i.e. ~64 B wasted per 1-child node [inference from formula; exact first-push size needs a `d8 --trace-elements-transitions` check — see open questions].
- `new Array(n)` preallocates exact capacity but permanently marks the array **`HOLEY_SMI_ELEMENTS`** (then `HOLEY_ELEMENTS` once you store objects) — [docs] https://v8.dev/blog/elements-kinds ("`const a = new Array(3)` … marked as `HOLEY_SMI_ELEMENTS`"). Preallocation saves copies but taints all later access with hole checks; V8 team comment: preallocate only when you know the size AND the holey cost is acceptable — [3rd-party] https://stackoverflow.com/questions/54481918/how-does-v8-optimise-the-creation-of-very-large-arrays (V8 engineer answer). For children arrays that are later traversed, holey is the wrong tradeoff [inference].
- `slice()` allocates **exactly** the needed capacity (no growth slack): fast path `HandleFastSlice → ExtractFastJSArray / AllocateJSArray(kind, map, length=count, capacity=count)`, `src/builtins/array-slice.tq`, `src/builtins/builtins-array-gen.cc` [source]. A scratch-stack + `slice()` therefore yields `PACKED_ELEMENTS`, exact-fit children arrays [inference].
- V8 **does** shrink backing stores, but only on explicit shortening, never by sweeping live objects: `ElementsAccessor::SetLengthImpl` / `pop` / `DeleteAtEnd` call `Heap::RightTrimFixedArray` when roughly `2*length <= capacity` (with pop-optimized trims), and length 0 canonicalizes back to shared `empty_fixed_array` (`initialize_elements()`), `src/objects/elements.cc` (`src/elements.cc` in older trees), `src/objects/fixed-array.cc` (`RightTrim/RightTrimOrEmpty/ShrinkOrEmpty`) [source]. Growing arrays never shrink by themselves.
- Dictionary elements (`DICTIONARY_ELEMENTS`, hash table) trigger on huge sparse indexes (gap ≥ `kMaxGap = 1024` heuristic in `ShouldConvertToSlowElements`, `src/objects/js-objects-inl.h`) [source] or `Object.defineProperty` indexed accessors — [docs] https://v8.dev/blog/fast-properties. Irrelevant if children are dense 0..n-1 [inference].

## 4. Allocation and GC: young gen, promotion, pretenuring, folding

- Default young-gen collector is the parallel semi-space copying **Scavenger**; **Minor Mark-Sweep is opt-in** (`--minor-ms`), not default — [docs] https://chromium.googlesource.com/v8/v8/+/HEAD/docs/heap/garbage-collection.md; code split `SemiSpaceNewSpace` vs `PagedNewSpace`, `src/heap/new-spaces.h` [source]. Parallel Scavenger since V8 6.2 (2017) — [docs] https://v8.dev/blog/orinoco-parallel-scavenger. Generational hypothesis + nursery→intermediate→old flow — [docs] https://v8.dev/blog/trash-talk.
- Sizes: each semi-space max `8 MB × kPointerMultiplier` (≈ **8 MB compressed / 16 MB uncompressed**; min 512 KB), computed in `Heap::MaxSemiSpaceSize/YoungGenerationSizeFromSemiSpaceSize`, `src/heap/heap.cc`, `src/heap/heap.h` [source]. MinorMS nursery (when enabled) is paged at tens of MB (`minor_ms_max_new_space_capacity_mb = 72` etc.) [source: `src/flags/flag-definitions.h`; 3rd-party explainer https://wingolog.org/archives/2023/12/08/v8s-mark-sweep-nursery]. So in workerd (Scavenger default) the whole young gen is on the order of **16 MB** — a multi-MB parse tree does not fit in it.
- Promotion after **2 survivals**: nursery → intermediate (first scavenge copy) → old gen (second scavenge), governed by the age mark (`ShouldBePromoted/IsAddressBelowAgeMark`, `src/heap/scavenger*.h`) — [docs] https://v8.dev/blog/trash-talk, https://v8.dev/blog/orinoco-parallel-scavenger. A fully-retained parse tree therefore gets **copied twice** by the Scavenger before settling in old space; that double-copy of every node + backing store is the dominant GC cost of eager tree building [inference].
- **Allocation-site pretenuring** avoids the double copy by allocating directly in old space once a site proves long-lived. Applies to **object/array literals** (`Runtime_CreateObjectLiteral/ArrayLiteral → CreateLiteral → AllocationSiteCreationContext`, `src/runtime/runtime-literals.cc`; nested `JSArray` literals get nested sites) [source]; tracked only for `JS_ARRAY_TYPE`/`JS_OBJECT_TYPE` when `allocation_site_pretenuring` is on (`AllocationSite::CanTrack`, `src/objects/allocation-site-inl.h`) [source]. Decision in `MakePretenureDecision/DigestPretenuringFeedback`, now `src/heap/pretenuring-handler.cc` (moved from `src/heap/heap.cc`): classic gate ≈ **≥100 creations (`kPretenureMinimumCreated`/`kMinMementoCount`) with ≥85% survival (`kPretenureRatio = 0.85`)** plus minimum new-space capacity (`kDefaultMinNewSpaceCapacityForPretenuring = 8192 KB × multiplier`), array pretransition capped at `kMaximumArrayBytesToPretransition = 8 KB`, `src/objects/allocation-site.h` [source]. `AllocationMemento` (one `allocation_site` field) rides trailing each object; `memento_create_count` vs `memento_found_count` feed the ratio [source]. Flags: `allocation_site_pretenuring=true`, `trace_pretenuring[_statistics]` (`src/flags/flag-definitions.h`) [source].
- How to make pretenuring kick in for the parser: allocate **all nodes at one object-literal site** and **all children arrays via one mechanism** (one literal or one `slice()` call path), parse documents big enough that the site sees ≥100 tenured instances with high survival, and keep the site monomorphic (same Map/ElementsKind — pretransitioning also specializes the boilerplate) [inference from the above]. Splitting node creation across N literal sites divides each site's creation count by N and can prevent the threshold from ever firing [inference]. I found no evidence that manually `new`-constructed class instances get literal-style pretenuring feedback in the same way; assume literals are the reliable path [no evidence found].
- **Allocation folding** (TurboFan `turbo_allocation_folding=true`, `src/flags/flag-definitions.h`; `memory-lowering.cc`, Turboshaft `memory-optimization-reducer.h`) [source] merges adjacent `AllocateRaw`s into one bump-pointer check + contiguous group (enabling write-barrier elimination — cf. the folded-allocation comment in `src/builtins/array-slice.tq` [source]). It does **not** eliminate the allocations; elimination needs escape analysis. So `node={}; node.name=…` is not folded away — but `node={name,attrs,children}` + `children=…slice()` in one hot function are adjacent allocations that fold the bump checks [inference].
- No `eval`/`new Function` is fine: none of this depends on them. Single-threaded parsing means no LAB contention issues [inference].

## 5. Design verdicts (smallest + fastest to build)

1. **Node shape: one object-literal site, fixed key order `{name, attrs, children}` (or shorter keys).** Beats `new Node()` class instances (no 7-instance slack bloat, no constructor IC warmup — [docs] https://v8.dev/blog/slack-tracking) and beats add-keys-one-at-a-time (N transitions per node vs 0 extra). Beats array tuples on memory (24 B vs 40 B/node compressed) and on API fit (DOM-style objects output). Tuple's only advantage is zero Map machinery during build; if parse-only microbenchmarks show tuple build significantly faster, consider building tuples internally and converting at the end — but that conversion pass costs more than it saves unless downstream never touches Maps either [inference — must benchmark].
2. **`attrs`: flat array `["k1","v1",…]` built on the scratch stack, not a per-node object.** A per-node attrs object with dynamic keys (`o[k]=v` loop) walks a new transition per distinct key order, megamorphs the site's Map family, and risks `fast_properties_soft_limit`/dictionary normalization on attribute-heavy elements — exactly the pathology §2 lists. A flat array has no Maps at all, one ElementsKind (`PACKED_ELEMENTS`), and zero transition work during parse. It costs ~2× bytes for the 1-attr case (32 B vs 16 B), but parse speed (priority 1) favors it; memory (priority 2) difference is bounded and exact-fit via `slice()`. Exception: if your corpus has a tiny fixed set of attribute shapes (e.g. always exactly `{id}`), a single-shape object literal can win — benchmark both [inference].
3. **No children ⇒ `null`, never `[]`.** Saves the 16 B `JSArray` shell per leaf; the backing is shared-empty either way, so `[]` is pure waste. `children: null` also keeps one Map (field representation just goes general `Tagged`) [inference].
4. **Single text child: store the string directly in `children` (overloaded `string | Array | null`) rather than a 1-element array, and rather than adding a 4th `text` field.** A 1-element array costs 16 + (8+4) = 28→32 B vs 0 B extra for the inline string (strings are slices of input per spec, no copy). A dedicated `text` field costs +4 B on *every* node (24→28→32 B after alignment for the common 3-field node) and an extra store per node. The polymorphism cost (3 shapes in one field) is paid at *traversal* time, not parse time, and parse time is priority 1 [inference — benchmark traversal if consumers are hot].
5. **Children collection: one shared scratch stack + `slice()` at close tag, not per-node `push`.** Wins on both axes: (a) memory — `slice()` gives exact-fit `PACKED_ELEMENTS` (`AllocateJSArray(len,len)` [source]), while per-node `push` growth (`NewElementsCapacity` 1.5×+16 [source]) leaves up to ~50% slack per node plus pays repeated alloc+copy per growth step; (b) speed — one alloc+copy per node vs O(log n) allocs+copies, one AllocationSite (pretenuring-friendly) vs per-node growth sites, and adjacent slice allocations fold bump checks. Keep the scratch stack itself `PACKED_ELEMENTS`: push/pop densely, never leave holes, never `new Array(n)` it, never read past `length` (OOB reads poison the load IC — [docs] https://v8.dev/blog/elements-kinds). Pre-size the scratch once (e.g. 1024) and let it grow; its backing is transient garbage either way [inference].
6. **Key/attr/text strings: `String.prototype.slice`/substring on the input (SlicedString, zero-copy view) — consistent with the "zero-copy slices" decision.** SlicedStrings keep the whole input alive (fine — results never outlive the request) and avoid copying; building via `+=` or `join` would copy. Whitespace-only text already dropped per spec (fewer nodes = less of everything) [inference; SlicedString representation — no V8 source link verified in this pass, needs confirmation].

## 6. How to measure object memory precisely

- **`%DebugPrint(obj)`** (map, instance size, in-object slack, elements kind, space): debug `d8` build, `d8 --allow-natives-syntax script.js`, special fns listed in `src/runtime/runtime.h` — [docs] https://v8.dev/blog/elements-kinds ("Debugging elements kinds"). Shows e.g. `[PACKED_SMI_ELEMENTS (COW)]`, `instance size`, `unused property fields` — [docs] https://v8.dev/blog/slack-tracking.
- **`--trace-elements-transitions`** (debug `d8`): logs every `PACKED→…→HOLEY` transition with location — [docs] https://v8.dev/blog/elements-kinds.
- **`--trace-gc-object-stats`** + `tools/heap-stats/index.html` visualizer; `--gc-interval=N` for finer sampling; major-GC datapoints only — [docs] https://v8.dev/docs/trace, https://v8.github.io/tools/head/heap-stats/index.html.
- **Heap snapshots**: Node `v8.writeHeapSnapshot()` / `v8.getHeapSnapshot()` — [docs] https://nodejs.org/docs/latest/api/v8.html; `v8::HeapProfiler::TakeHeapSnapshot()` — [docs] https://v8.github.io/api/head/classv8_1_1HeapProfiler.html. Diff snapshots (empty doc vs N-node doc) ÷ N = bytes/node.
- **In workerd/Workers none of the flags exist** (no `--allow-natives-syntax`, no `--trace-*`, no `--gc-global`). What works: local `wrangler dev` + DevTools `Memory > Take snapshot` / `Profiler` for CPU+GC share — [docs] https://developers.cloudflare.com/workers/observability/dev-tools/memory-usage/, https://developers.cloudflare.com/workers/observability/cpu-usage/; `performance.now()` deltas (note: in production it only advances on I/O; locally under `wrangler dev` timers advance so CPU microbenchmarks are possible) — [docs] https://developers.cloudflare.com/workers/runtime-apis/performance/; dashboard memory P50/P90/P99 + `exceededMemory`/`Error 1102` tracking for regressions — [docs] https://developers.cloudflare.com/workers/platform/limits. Practical proxy: measure exact bytes in a local `d8`/Node pinned near V8 15.1, measure speed in `wrangler dev` + production shadow traffic [inference].

## Actionable rules for the parser

- Workerd = pointer compression on: budget **24 B/node shell, 16 B/array shell, 8 B + 4 B/slot backing**; `null` = 0 B, empty array/object backing = 0 B (shared `empty_fixed_array`).
- Exactly **one** node literal site, fixed key order (`{name,attrs,children}`); never add keys later, never `delete`, never `__proto__` keys, never mix `{}` and `Object.create(null)` prototypes.
- `attrs` = flat exact-`slice()`d array (or `null` when absent); do not build per-node objects with dynamic keys.
- No children ⇒ `children: null`; single text child ⇒ inline the string in `children`, no 1-array, no extra `text` field (benchmark if traversal is hot).
- Children via **shared scratch stack + `slice()` at close tag**; keep scratch densely packed, never `new Array(n)`, never OOB reads, never holes.
- Make documents large enough in benchmarks that literal sites pass the ~100-instance pretenuring gate; keep node/children allocation sites monomorphic so instances pretenure to old space and skip the Scavenger double-copy.
- All strings are input `slice()`s; drop whitespace-only text (already decided) — it directly deletes nodes.
- Measure sizes in local `d8 --allow-natives-syntax` (`%DebugPrint`, `--trace-elements-transitions`, `--trace-gc-object-stats`); measure speed/memory regressions with `wrangler dev` DevTools snapshots + dashboard `exceededMemory`.

## Open questions that need a benchmark (in workerd, not just `d8`)

1. Node literal vs array tuple build speed and peak RSS on 10 KB / 1 MB / 10 MB docs (does Map machinery cost more than 16 B/node saves?).
2. `attrs` flat-array vs single-shape object literal on attribute-heavy corpus (parse ns/byte + bytes/attr).
3. Scratch+`slice()` vs per-node `push` vs count-then-`new Array(n)`+fill: parse time, peak young-gen churn, and downstream traversal time (`PACKED` slice vs `HOLEY` prealloc).
4. Overloaded `children: string|Array|null` vs dedicated `text` field: parse time + consumer traversal time (polymorphism cost at use sites).
5. First-push backing size for `[]`+`push` (is a 1-child node really sitting on ~16 slots?) via `--trace-elements-transitions`; scratch pre-size sensitivity (256 vs 1 K vs 16 K).
6. Pretenuring verification: does the single node-literal site actually reach `kTenure` under `--trace-pretenuring-statistics` in `d8`, and does parse time/MB drop after warmup? What is the minimum doc size × request count for it to engage under workerd's Scavenger sizing?
7. Key length: do shorter keys (`{n,a,c}`) measurably help (smaller input slices? no — keys are constants; only descriptor/Map memory + IC strings)? Likely noise — verify once.
8. SlicedString vs flattened-string memory for attr/text values at scale (does retaining the whole input per value hurt 128 MB headroom on 10 MB docs?), and `slice()` vs manual index-pair deferred materialization.
