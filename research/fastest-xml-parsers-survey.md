# Fastest XML parsers: techniques survey for a V8 / Workers DOM parser

> Context: pure-JS, whole document in memory (`string | Uint8Array/ArrayBuffer`), eager DOM `{name, attrs, children}` in document order, zero-copy slices, whitespace-only text dropped, speed > memory, Web APIs only, 128 MB/isolate, CPU limits, no `eval`, WASM only precompiled. Target workerd 1.20260815 / V8 15.1, `compatibility_date 2026-08-01`.
> Label key: `[source]` verified in code/spec, `[docs]` maintainer statement, `[3rd-party]` others' bench/blog, `[inference]` my reasoning. "No evidence found" is stated explicitly where applicable.

## 0. What V8 12+ (2023–2026) rewards — read this first

Old (pre-2019, Crankshaft-era) advice that is **outdated for V8 12+ / Turbofan+Maglev** is flagged `OUTDATED`.

1. **Single-char `indexOf` is `memchr` in C++.** `String.prototype.indexOf` 1-char needle on one-byte strings goes through `StringBuiltinsAssembler::StringIndexOf` → `libc_memchr` [source] https://chromium.googlesource.com/v8/v8/+/439a8edcf77947777c5c757b0dec0363d9446093/src/builtins/builtins-string.cc — up to 5x speedup noted in that CL (2016, still present in `main` in 2026). Applies to V8 15.1 [inference — verified in `main` branch Sep 2026]. Multi-char needles fall back to `Runtime::kStringIndexOfUnchecked` (`src/runtime/runtime-strings.cc`) [source] https://github.com/v8/v8/blob/main/src/runtime/runtime-strings.cc.
2. **Zero-copy slices are views, threshold 13 chars.** `SlicedString {parent, offset, length}`, `ConsString {first, second}`; `SlicedString::kMinLength = 13`, `ConsString::kMinLength = 13`, `String::kMaxSize = 512MB-1` [source] `src/objects/string.h` https://github.com/v8/v8/blob/main/src/objects/string.h. Slices `<13` chars are copied; longer are O(1) views that **pin the parent** ("missing: truncating sliced string to enable otherwise unneeded parent to be GC'ed") [source] same file + https://chromium.googlesource.com/v8/v8/+/HEAD/docs/objects/strings.md. For your design (results never outlive request, input kept alive anyway) this is pure win [inference].
3. **`charCodeAt` dispatch, not `charAt` + string compare.** `charCodeAt` lowers to `StringCharCodeAt` (word32); `charAt` lowers to `StringCharAt` → `CharCodeAt + FromCharCode` (allocates 1-char string) [source] https://chromium.googlesource.com/v8/v8/+/05f5ebce2f34753d0fb32fd2f3b6e652c8682e09%5E%21/ (2016, still current). Prefer `s.charCodeAt(i)===60 /*<*/` [inference, standard since 2012].
4. **Monomorphic objects.** Objects with same props added in same order share a `Map` (hidden class); IC sites go `UNINITIALIZED→MONOMORPHIC→POLYMORPHIC(≤4)→MEGAMORPHIC` to stub-cache/dictionary fallback [docs] https://chromium.googlesource.com/v8/v8/+/e74e6c524cb1065141b103edf8b9bb9fec5cdadf/docs/runtime/hidden-classes-and-ics.md and https://github.com/v8/v8.dev/blob/main/src/blog/fast-properties.md (2017, still valid in V8 15 [inference]). So always construct `{name, attrs, children}` in that order, never add/remove shapes conditionally [inference].
5. **Regex is Irregexp (backtracking JIT by default).** `/(a*)*b/` never finishes; mitigation flags `--enable-experimental-regexp_engine-on-excessive-backtracks`, `backtracks-before-fallback=50000`, opt-in `/l` linear flag (Chrome 135+/Node 22+) only without backrefs/lookaround/`u`/`i` [docs] https://v8.dev/blog/non-backtracking-regexp, arch https://github.com/v8/v8/blob/main/docs/regexp/architecture.md (2024). `OUTDATED`: "regex is always slow" — modern Irregexp has Boyer-Moore/QuickCheck fast paths, but **adversarial patterns still cliff** — keep regex out of the hot loop [inference].
6. **Workers limits.** Isolates, not processes [docs] https://developers.cloudflare.com/workers/reference/how-workers-works; 128 MB/isolate incl. heap+WASM, free 10 ms CPU/req, paid 30 s default up to 5 min, CPU = execution only [docs] https://developers.cloudflare.com/workers/platform/limits. No Node `Buffer`, no native addons. Changelog showed V8 14.8 on 2026-04-27; no public 15.1 entry found at research time — **state tested V8 explicitly** (`process.versions.v8` / `workerd --version`) [3rd-party verification gap].

On `ideas.md #0-8`: depth-first with an explicit open-element stack (fail if mis-nested or `stack>0` at EOF) is the only correct eager-DOM strategy [inference]. Breadth-first requires the full tree anyway + extra queue; recursive-from-both-ends cannot validate nesting without meeting in the middle (O(n²) shifts); regex-alone cannot match nesting (Chomsky) and cliffs (see §4); ad-hoc `children/paths/parents` laziness contradicts the already-decided eager model — useful only as a *later* query API on top of the eager tree.

## 1. JavaScript parsers

### 1.1 txml (`TobiasNickel/tXml`) — fastest pure-JS DOM reference

- Core: `src/tXml.js` `parse(S)→parseChildren→parseNode/parseText/parseName` [source] https://github.com/TobiasNickel/tXml/blob/master/src/tXml.js. Technique: `charCodeAt(pos)===60/62` dispatch + `indexOf('>',pos)`, `indexOf(']]>',pos)`, `indexOf('-->',pos)` jumps; `slice/substring` for names/text; monomorphic `{tagName,attributes,children}`; no regex in hot path (only optional entity decode) [source] + author notes [docs] https://tnickel.de/2020/08/30/2020-08-how-the-fastest-xml-parser-is-build.
- Output: DOM array + `simplify/filter/getElementById/transformStream` [docs] same repo README.
- Skips: fault-tolerant, no validation; close-tag check is only `closeTag.indexOf(tagName)===-1`; DOCTYPE raw; entities off by default; no NS resolution, no DTD expansion; trims whitespace unless `keepWhitespace` [source].
- Bench (self-reported, caveat: no HW/dataset, unequal work): `tXml 100 ms 1x | FXP 250 ms 2.5x | xml2js 800 ms 8x | DOMParser 95 ms` [docs] README.

### 1.2 fast-xml-parser v4/v5 (`NaturalIntelligence/fast-xml-parser`)

- Core: `src/xmlparser/OrderedObjParser.js` `parseXml()` `for(i...)` + `charCodeAt(i+1)` dispatch (`47:/,63:?,33:!`), `findClosingIndex(indexOf)` for `>/-->/]]>/?>`, quote-aware `readTagExp` [source] https://github.com/NaturalIntelligence/fast-xml-parser/blob/master/src/xmlparser/OrderedObjParser.js; attrs via regex `([^\s=]+)\s*(=\s*(['"])([\s\S]*?)\3)?` in `src/xmlparser/XMLParser.js`, `DocTypeReader.js`, `util.js#getAllMatches` [source].
- v4→v5 delta: same features [docs] CHANGELOG; v5 splits builder, `strnum≥2.3`, `@nodable/entities` single-scan (~8–10% when `processEntities:true` v5.7.0), `is-unsafe`, `xml-naming`, `ExpressionSet` stopNodes, validator quadratic fix v5.11.1 [source] CHANGELOG.
- Output: JSON (`compact` vs `preserveOrder` array) + validator + builder [docs].
- Skips (configurable): entities/DOCTYPE/NS/value-coercion all optional; cheapest is all-off [docs].
- Bench: README `XMLParser_v4.png` req/s only, no absolute table [docs]; independent `parse-xml-benchmark` has FXP slowest on med/large (see 1.6); `ts-xml` claims 3.6–6.3x over FXP [3rd-party]. Caveat: JSON+coercion vs DOM/SAX is unequal work.

### 1.3 htmlparser2 tokenizer (`fb55/htmlparser2`)

- Core: `src/Tokenizer.ts` (~1150 lines) `write()`, `stateIn*()`, `getSection()`, `emitCodePoint()` [source] https://github.com/fb55/htmlparser2/blob/master/src/Tokenizer.ts; `src/Parser.ts`, `entities/decode` trie.
- Technique: streaming char-state-machine, `charCodeAt` + `sectionStart` slicing; **no `indexOf` fast path** (needed for `<script/style`, `--`, `]]>` correctness) [source]. Pause/resume.
- Output: SAX (`onopentag/ontext/...`) + DOM via `domhandler/domutils` [docs].
- Skips: forgiving, non-validating even in `xmlMode`; no DTD/XSD [docs].
- Bench via `AndreasMadsen/htmlparser-benchmark` real sites [3rd-party] https://feedic.com/htmlparser2: `htmlparser2 2.17 ms/file | node-html-parser 2.35 | parse5 9.70 | saxes 45.79` — caveat: HTML corpus, GH-Actions variance.

### 1.4 sax (`isaacs/sax-js`) / saxes (`lddubeau/saxes`, archived 2025-12-31)

- sax core: `lib/sax.js` `write()` `switch(state)` (~35 states `S.BEGIN…S.TEXT_ENTITY`) + `openTag/closeTag/attrib/parseEntity` [source] https://github.com/isaacs/sax-js/blob/main/lib/sax.js. Char-by-char, regex only for name/entity classes; inner fast loops for `S.TEXT` (`while(c&&c!=='<'&&c!=='&')`) and `CDATA` [source]. `textNode+=c` accumulation (ConsString cliff).
- saxes core: `src/saxes.ts` `write/_write`, `charCodeAt` + surrogate handling ("using charCodeAt…faster"), 45 states, `xmlchars` tables not regex in hot loop [source] https://github.com/lddubeau/saxes/blob/master/src/saxes.ts. Fork of `sax@1.2.4`, stricter yet ~2.45x faster by redesign [docs].
- Output: SAX only, Node Stream (sax) / EventEmitter (saxes) [docs].
- Skips: sax "little validation in strict" [docs]; DTD raw; 5+HTML entities; NS only if `xmlns:true`. saxes enforces XML 1.0 5th/1.1 2nd + NS well-formedness but "DTD internals not thoroughly parsed" [docs].
- Bench (`sax-wasm` 3 MB mean-of-10) [source] https://github.com/justinwilaby/sax-wasm: `sax-js 26.99 ms | saxes 11.00 | sax-wasm 6.80`. Caveat: position/error-resume cost, chunk size matters.

### 1.5 `@rgrove/parse-xml` — best *correct + fast* pure-JS template

- Core: `src/lib/Parser.ts` `parse/consumeElement/consumeCharData/consumeComment/consumeCdata/consumeReference/consumeProlog`, `src/lib/StringScanner.ts` (`consumeUntilString/consumeUntilMatch`), `src/lib/syntax.ts` (`endCharData=/<|&|]]>/`, `isNameChar` via `codePointAt` ranges) [source] https://github.com/rgrove/parse-xml/blob/main/src/lib/Parser.ts.
- Output: typed tree `XmlDocument>XmlElement/XmlText/XmlCdata/...` with `parent/start/end`, `toJSON()` [docs].
- Skips: non-streaming non-validating but conformant; DTD discarded unless `preserveDocumentType`; only 5 predefined entities (else throw); UTF-8 only; qualified names, no NS resolution; passes relevant XML Conformance Suite tests [docs].
- Bench (author-run M1 Max Node 22, caveat: DOM vs JSON unequal, native startup dominates small) [docs] `rgrove/parse-xml-benchmark`: small 291 B `parse-xml 253k ops/s | FXP 127k | libxmljs2 68k`; med 72 KB `libxmljs2 1915 | parse-xml 1350 | FXP 560`; large 1.1 MB `libxmljs2 182 | parse-xml 109 | FXP 48`.

## 3. Ranked techniques to adopt (pure-JS DOM on V8 15.1)

1. **`indexOf` jumps, never char-by-char.** `pos=indexOf('<',pos)`, `indexOf('>',pos)`, `indexOf(']]>'/ '-->'/'?>',pos)` — single-char case is `memchr` (§0). This is the txml/parse-xml/xmldom/saxen pattern and the #1 speedup over sax-style per-char loops [source+inference]. Depth-first loop: text until `<` → dispatch on `charCodeAt(pos+1)` (`/ ? !` + letter) → jump to `>`/`-->`/`]]>`/`?>` → push/pop stack.
2. **`charCodeAt` integer dispatch + 256-entry class table.** `const T=new Uint8Array(256)` mapping `< & > " ' = / ? ! - [ whitespace` classes (pugixml `chartype_table` idea in JS; saxes `xmlchars`, saxe `chars.ts`) [source]. Avoids regex and `charAt` allocs (§0).
3. **Zero-copy `slice` for names/text/attr values; drop whitespace-only text without copying twice.** Slices ≥13 chars are views (§0) — exactly your "strings are slices" decision. Test `s.slice(a,b)` then `trim`-check via `charCodeAt` scan first; only `slice` survivors. Never `+=` accumulate text (ConsString flatten cliff) [inference].
4. **Monomorphic `{name,attrs,children}` + arrays as stacks.** Same key order every node; `attrs` always object (even `{}` — or `null` consistently; measure), `children` always array; explicit `stack=[]` + `stack.push/pop` (depth-first per ideas.md), iterative not recursive (avoids RangeError ~12–13k depth, see §4) [docs+inference].
5. **Quote-aware tag scan without regex.** Manual `while` to matching `>` skipping `"..."`/`'...'` (OrderedObjParser `readTagExp`, quick-xml `ElementParser`) [source]. Attr parse = manual scan to `=` + quoted slice; **no per-attr regex** (FXP's attr regex is a known cost + ReDoS surface) [inference].
6. **Lazy/optional work behind flags (RapidXML `Flags` idea).** `entities:false`, `comments:false`, `pi:false`, `doctype:skip`, `namespaces:false` default-off; single-pass entity decode only if `&` present (`indexOf('&')` guard + `@nodable/entities`-style single scan) [source+inference].
7. **One-pass, single `write`, pre-sized structures.** saxes: single-`write` fastest [docs]; htmlparser2 `onopentagname/onattribute` (no attrib object) vs `onopentag` [source]; saxen lazy `attrGetter()` [source]. Eagerly `push` in document order; don't build intermediate token arrays.
8. **Bytes path: `TextDecoder.decode` once, then parse the string.** Parsing `Uint8Array` directly in JS means per-byte `get`/bounds checks; V8 string ops (`indexOf/memchr`, `slice` views) are C++ [inference]. No evidence a pure-JS byte scanner beats string scanning on V8 15 — must benchmark (§6 Q1). Offer both entry points, share the core via string.
9. **ASCII fast path + UTF-16 fallback.** pugixml's `0x80808080` 4-B ASCII check [source]; in JS: `charCode<128` fast comparisons, `codePointAt` only on demand (parse-xml `isNameChar`) [source]. V8 one-byte vs two-byte strings already split fast paths (§0) [inference].
10. **Bounds-check hoisting / length caching.** `const len=s.length; while(pos<len)` with local `s` (lets Turbofan hoist; `OUTDATED`: Crankshaft-era `try/catch` fears — structured `if/throw` is fine on V8 12+) [inference].

Explicitly **do not adopt**: per-char SAX state machines with 35–45 states (correct but slowest in every bench, §1.4); regex tokenizers (ReDoS + backtrack cliffs, §4); `+=` text accumulation; validating/DTD/XSD/XPath in the hot loop; native-addon or JIT-WASM hype without measuring crossing cost on 10 ms budget.

## 5. Pitfalls (correctness + security + cliffs)

- **Entity expansion (billion laughs / quadratic / numeric bypass).** FXP: CVE-2026-26278 unlimited DOCTYPE expansion (fix ≥5.3.6/4.5.4, workaround `processEntities:false`) [source] https://www.cve.org/CVERecord?id=CVE-2026-26278; CVE-2026-33036 numeric-entity bypass (`&#65;×1M→147 MB` even with limits; fix ≥5.5.6/4.5.5) [source] https://github.com/advisories/GHSA-8gc5-j5rx-235r; CVE-2026-25896 `.` as regex wildcard shadows `&lt;` (XSS; fix ≥5.3.5) [source] https://nvd.nist.gov/vuln/detail/CVE-2026-25896; expat CVE-2023-52425 large-token quadratic reparse (fix ≥2.6.0), CVE-2024-8176 linear-entity-chain stack overflow (fix ≥2.7.0) [source] https://nvd.nist.gov/vuln/detail/CVE-2023-52425 + https://github.com/libexpat/libexpat/issues/893. **Rule: default `entities:false` or cap `maxTotalExpansions/maxExpandedLength/maxDepth`; never regex-expand numerics in a loop.**
- **ReDoS.** FXP `currency.js` CVE-2024-41818 [source] https://nvd.nist.gov/vuln/detail/CVE-2024-41818; `html-parse-stringify2` CVE-2021-23346, Python `html.parser` CVE-2025-6069 same class [3rd-party]. No regex on attacker input in hot path.
- **Serializer injection.** xmldom family: CVE-2026-34601 (`]]>` verbatim), CVE-2026-41675 (`?>`), CVE-2026-41674/41672 (DOCTYPE/comment), CVE-2026-41673 recursion (~12–13k depth RangeError) [source] https://nvd.nist.gov/vuln/detail/CVE-2026-34601 + https://github.com/xmldom/xmldom/security/advisories/GHSA-2v35-w6hq-6mfw; FXP builder CVE-2026-41650 (`-->`/`]]>` unescaped), CVE-2026-27942 `preserveOrder` stack overflow [source] NVD. Fuzz round-trips.
- **Proto-pollution.** xml2js CVE-2023-0842 (`__proto__` keys; fix ≥0.5.0) [source] https://security.snyk.io/vuln/SNYK-JS-XML2JS-5414874. Use `Object.create(null)` for attrs or guard `__proto__`.
- **Quadratic attrs / namespaces.** quick-xml RUSTSEC-2026-0194 (80k attrs ~6 s, 800k ~10 min; fix hash pre-filter ≥0.41.0) + RUSTSEC-2026-0195 (NsReader 3x heap before first event; cap 256) [source] https://rustsec.org/advisories/RUSTSEC-2026-0194.html. Cap attrs/decls even in JS.
- **Slice-pinning / `+=` cliffs.** Slices pin parents; `+=` builds Cons trees then flattens (copy spike over CPU limit) (§0). Test many-small-slices vs copies; FXP `textData+=c` is the anti-pattern [source+inference].
- **libxml2/expat CVE noise** (XXE CVE-2024-40896, UAF CVE-2024-25062, stack-BOF CVE-2025-24928/6021, XPath recursion CVE-2025-9714) [source] NVD — not Workers-runnable, but defines the conformance/security test list to borrow.
- **Name collision:** `pug` JS template CVEs (CVE-2021-21353, CVE-2024-36361) are **not** `pugixml` CVEs — no pugixml CVE found [source] https://github.com/zeux/pugixml. Footnote it to avoid misattribution.

## 7. Actionable rules for the parser

- Depth-first single pass with explicit `stack[]`; `indexOf`-jump to next structural char; `charCodeAt` dispatch; `slice` views for names/text/values; drop whitespace-only text via pre-scan.
- Attribute scan manual + quote-aware; no regex in/parser hot loop; single entity pass guarded by `indexOf('&')`, default off or capped.
- Monomorphic nodes (`{name,attrs,children}` same order), arrays only, iterative (no recursion), `Object.create(null)` or `__proto__` guard for attrs.
- `string` entry point primary; `Uint8Array/ArrayBuffer` → single `TextDecoder.decode` then same core (verify by bench).
- Flags object fixed at construction (`entities/comments/pi/doctype`) so Maglev specializes; separate slow paths (`noinline`-style cold functions) for comments/PI/DTD.
- Caps from day one: max depth (e.g. 1000, cf. Jackson precedent [3rd-party]), max attrs/tag, max expansions/expanded length, max text/token length; throw, don't hang.
- Fuzz: nested/quadratic/numeric entities, `-->`/`]]>`/`?>` injections, deep nesting, 100k attrs, multi-root, lone `<`/`&`, split-chunk inputs.

## 8. Open questions that need a benchmark (in workerd, V8 15.1)

1. String vs bytes: is `TextDecoder.decode` once + string-parse faster than direct `Uint8Array` scan at 1 KB / 100 KB / 10 MB?
2. `slice` vs copy for retained strings: at what count/size does parent-pinning OOM the 128 MB isolate? Does explicit `(' '+s).slice(1)`-style copy ever win?
3. `indexOf('<')` loop vs one `indexOf` per token vs pre-collected structural index (simdxml-style two-pass in JS)?
4. Attr model cost: `attrs:{}` vs `attrs:null`-when-empty vs parallel arrays vs lazy getter (saxen-style) for DOM output?
5. `children` array growth: `push` vs pre-sized `new Array(n)`; wide (10k siblings) vs deep (10k depth) shapes?
6. Entity handling cost: off vs `&`-guarded single-scan vs `@nodable/entities`; numeric `&#...;` loop cost on adversarial input?
7. Text accumulation: slice-per-segment vs join-at-close vs `+=` — where is the flatten cliff on 1 MB text nodes?
8. Class-table (`Uint8Array[256]`) vs chained `charCodeAt===` — measurable on Maglev?
9. WASM (precompiled tokenizer) vs pure JS: does JS↔WASM crossing + init beat `memchr`-backed `indexOf` within 10 ms/30 s CPU budgets?
10. Depth/attr/entity caps: what limits keep worst-case under CPU budget without regressing common-case throughput >5%?
